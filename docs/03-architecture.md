# 架构与数据设计（建议稿）

## 1. 技术方向

考虑 2 人团队，采用模块化单体：统一部署后端，按业务模块隔离代码和数据访问。先降低跨服务事务和运维负担；有实际瓶颈及独立维护能力后再拆分。

- 后端：C#、ASP.NET Core，启动开发时选择仍受支持的 .NET LTS 并锁定版本。
- 前端候选：Blazor Web App；通过扫码、打印、弱网和终端浏览器验证后确定。若团队已有成熟前端能力，可另评估 Vue/TypeScript。
- 数据库候选：PostgreSQL 或 SQL Server，依据运维能力、授权成本和恢复演练选定其一；一期不维护双数据库适配。
- 数据访问：EF Core；关键库存路径显式控制事务和并发。
- API：HTTP JSON、OpenAPI，设备/打印适配独立接口。
- 部署：工厂内网应用服务和数据库，HTTPS、受控远程访问、独立备份位置；具体机器数量待可靠性评估。
- 一期不默认引入 Redis、消息中间件、Kubernetes 或数据湖。

以上没有执行软件安装，也未完成技术验证；立项后需做小型技术验证并记录最终版本。

## 2. 模块与依赖

建议模块：Identity、MasterData、Purchasing、Sales、Inventory、Manufacturing、Quality、Traceability、Reporting。

各模块划分 API、应用用例、领域规则及基础设施。不要为每个简单 CRUD 堆叠额外抽象。模块通过明确的应用接口协作，禁止跨模块直接修改业务表。

同步业务如领料和库存扣减在同一数据库事务内完成。异步通知或报表同步可使用事务发件箱 Outbox，由后台任务重试；消费方以事件 ID 去重。先定义事件用途，再引入机制。

## 3. 核心数据概念

| 领域 | 主要实体 | 关键约束 |
| --- | --- | --- |
| 公共 | Factory、User、Role、AuditLog | 业务数据带工厂归属，服务端校验范围 |
| 主数据 | Material、Unit、Supplier、Customer | 编码唯一，停用不删除历史 |
| 工艺 | BomVersion、BomItem、RouteVersion、RouteStep | 工单引用已批准版本并保留快照 |
| 采购 | PurchaseOrder/Line、Receipt/Line | 收货与订单行关联，累计数量校验 |
| 库存 | Warehouse、Location、Lot、StockBalance、StockLedger、Reservation | 库存维度及库存状态统一定义 |
| 生产 | WorkOrder、MaterialIssue、Consumption、UnitSerial、OperationRecord | 工单、消耗、单件记录可追溯 |
| 品质 | Inspection、TestResult、Defect、Repair、Disposition | 放行依据明确，返修保留历次记录 |
| 包装出货 | Package、PackageMembership、SalesOrder、Shipment/Line | 包装关系保留历史，出货 SN 唯一控制 |

这些是概念模型，详细 ER 图、字段字典、索引与迁移脚本需在需求确定后编制。

## 4. 库存与并发设计

库存流水是不可变业务事实；余额是可重建的查询与并发控制结果。一次库存变更必须在同一事务中完成：校验单据和状态 → 校验幂等键 → 获取并发控制 → 写流水 → 更新余额 → 推进单据状态 → 提交。

余额需通过行锁或带版本号的条件更新防止并发超扣；不能只在应用内先查后减。流水唯一业务键、SN 唯一约束、请求幂等键必须由数据库约束兜底。

发料位置转移、实际消耗、退料、报废采用不同业务类型。已过账错误用反向流水冲销，禁止直接修改历史。定期用流水重算余额并形成差异告警。

## 5. 状态与接口约定

- 单据与实体分别建状态机；采购订单、库存单据、工单和整机不得共用一套通用状态。
- 提交、审批、放行、过账、冲销采用明确操作；每个操作定义前置状态和权限。
- 写入接口支持幂等键，错误返回稳定业务码及可读信息；不得暴露堆栈或敏感信息。
- 列表分页，导出受权限和数量限制；接口带关联 ID 便于追踪。
- 设备导入包含设备 ID、测试时间、SN、项目、数值、单位、判定和原始报文关联。
- 设备判定与系统放行规则冲突时进入异常队列；不能静默覆盖。

## 6. 安全与运行

使用成熟认证组件，密码安全散列；避免自制密码学。服务端执行角色及数据范围校验，数据库账号最小权限，密钥不提交仓库。上线前建立日志、健康检查、磁盘容量、任务失败与备份失败告警。

数据库迁移必须在预发布环境验证。应用回退与数据库回退分别设计；发生新业务写入后，不能直接恢复旧备份而丢弃已产生记录。
